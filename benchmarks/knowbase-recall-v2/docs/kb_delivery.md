# KnowBase 发布任务可靠投递

发布状态与 Outbox 任务在同一个 PostgreSQL 事务内保存。RabbitMQ 暂时停机时，发布仍然可以完成，任务保留在数据库等待投递。

Relay 轮询 Outbox，使用 SKIP LOCKED 避免多个 Relay 争抢同一条记录，收到 RabbitMQ publisher confirm 后才标记为已投递。

系统采用至少一次投递。Broker 已确认而数据库标记失败时会重复发送；消费者依靠 event_id 对应的 receipt 完成记录跳过重复副作用。

失败处理采用持久化重试，默认最多处理 3 次，重试间隔为 5 秒、10 秒。持续失败的消息进入对应的 .dead 死信队列，避免无限重试。

死信可以在核对文档状态和失败原因后人工重放。完成 receipt 的保留期限必须覆盖可能的重投窗口，不能过早删除去重记录。

## 排查发布成功但索引没有更新

先检查业务发布是否确实提交，再查看该事件是否仍停留在数据库待投递列表。数据库中没有任务与 Broker 尚未收到任务，是两种不同的故障位置。前者需要核对发布事务，后者需要检查投递连接和 Relay 的工作情况。不要在不了解故障位置时反复点击发布，否则会创建新的独立事件，增加排查难度。

如果某条消息已被 Broker 接收，却仍然没有对应结果，应检查目标队列、消费者连接和处理记录。服务进程活着并不能证明某条管线正在正常消费。也不要把队列中没有可见消息直接解释为处理成功，因为消息可能处于未确认状态，仍被某个消费者持有。

确认消息已经完成后，也应分别检查各条管线。全文可见并不代表向量和图谱都已经处理完成。一次重建可能涉及不同的外部服务，故障原因与处理耗时也不相同。诊断报告应写明具体队列和事件，避免只记录“索引坏了”这种无法定位的描述。

## 重复、超时与人工操作

重复投递是正常的恢复路径之一。排查时需区分同一个事件的再次投递，与管理员另行发起的新重建事件。二者对完成记录的匹配方式不同。人工操作也应保留可追溯记录，不能直接修改完成状态来伪造成功，否则下一次恢复时可能失去正确的处理依据。

超时故障还要区分业务处理失败和结果响应丢失。外部服务可能已经保存部分数据，消费者却没有收到成功响应。后续恢复必须结合索引自己的隔离与激活规则，不能仅依赖消息投递次数判断所有副作用都已撤销。对无法立即回收的不可见批次，应保留诊断信息，等待安全的清理流程。

人工恢复前，应先判断外部依赖是否已经修好。未修复的故障直接重放，通常只会再次消耗重试次数并产生相同的死信。修好后也要核对目标文档状态，因为任务创建时与恢复时可能已经是不同修订。对过期任务，跳过可以是正确结果，无须为了让旧任务“成功”而覆盖当前文档。

恢复死信前先修复失败原因，再确认文档仍存在且版本适用，最后人工创建新的投递事件。
