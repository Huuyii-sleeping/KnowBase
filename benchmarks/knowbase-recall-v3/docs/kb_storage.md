# KnowBase 分层存储说明

KnowBase 将结构化元数据、长正文和二进制对象分开保存。

PostgreSQL 的 kh_document 保存标题、文件名、版本、审核状态、权限和当前 content_id。MongoDB 的 document_content 保存完整 Markdown、解析警告和资源引用。RustFS 通过 S3 兼容接口保存原始文件和提取出的图片等资源。

PostgreSQL 与 MongoDB 通过 content_id 关联。文档列表只读 PostgreSQL，打开详情时才按 content_id 读取 MongoDB 的长正文。

原始文件的对象键位于 original/ 前缀，提取资源的对象键位于 assets/ 前缀。资源通过带权限检查的应用对象代理访问。

这三种存储没有共同的分布式事务。后续持久化失败时，需要清理已经创建的资源，并保留无法确定提交结果的数据以便核对。

## 从列表到详情的排查顺序

如果列表里已经能看见文件名，而详情页没有正文，首先检查当前元数据记录引用的正文标识。文件名只是展示字段，不能用来猜测正文的关联关系。还需要确认请求者有权限访问该文档，再检查正文存储连接和该标识对应的记录。一次详情查询失败并不自动意味着原始文件已经丢失，因为原文件保存在另外的对象存储中。

如果用户可以打开正文中的图片链接，但无法下载原文件，需要分别检查两种对象键和对应的访问入口。正文中出现了某个 URL，不代表服务端已经校验过所有后续访问。实际资源请求仍须经过应用代理的鉴权，不能把对象存储的内部地址直接当成公开下载地址交给用户。

如果需要导出一份可恢复的数据备份，应该考虑三类持久化资源之间的引用关系。只备份文档表只能恢复列表信息，不能保证恢复正文和二进制文件；只复制对象文件也无法恢复审核状态和权限。恢复操作应在受控环境里校对引用，避免把不同时间点的数据误认为同一份完整快照。

## 修改与故障处理

用户编辑的是标准化正文，而原始二进制文件用于追溯上传来源。二者用途不同，因此不能仅凭原文件是否变化判断详情内容是否已经更新。排查修订问题时，需从当前正文引用开始检查，而不是任意选择同一文档关联的某条历史记录。

操作超时时，客户端看到的错误不能完全代表远端提交结果。服务端可能已经提交成功，只是响应未能返回。清理策略应先检查提交后实际引用，再决定是否删除刚刚创建的正文；在无法确认结果时保留资源，比误删正在使用的数据更容易恢复。

后台清理程序也应有明确边界。原始文件与提取资源可能采用不同生命周期，不能只根据某个时间戳批量删除所有对象。对于已经被正文引用的图片，应先理解其归属与访问规则。当前版本的资源回收边界由对应的清理流程决定，操作人员不应自行推断所有对象都可以立即删除。

定位跨存储故障时，排查顺序是核对元数据引用、确认正文记录、检查对象键，再判断是否需要补偿；不要先删除数据再寻找关联关系。
