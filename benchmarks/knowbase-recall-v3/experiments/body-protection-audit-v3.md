# 标题上下文下的正文候选保护

本轮推荐的显式候选配置为 `title-heading + body-reserve + cjk + 15:15`。在这份冻结语料上，它找回标题上下文造成的旧题候选证据损失，同时保留标题依赖题的收益。默认配置仍为 `body + combined + standard`，本轮没有部署业务环境或重建业务文档。

## 范围与复现

冻结协议为 [body-protection-protocol.json](body-protection-protocol.json)，在测量前提交；机器可读汇总、逐证据获得/损失与已知问题的阶段记录见 [body-protection-results.json](body-protection-results.json)，选型见 [body-protection-decision.json](body-protection-decision.json)。此前的[上下文对照](context-audit-v3.md)保持原样，本报告继续处理其中已发现的正文退步。

4 种配置 × 2 对预算 × 224 道题，共 **1792 次计分 IPC 请求**，不含预热与 HTTP 一致性抽查。每轮单独建立临时索引，完整运行 development 96、regression 80 和已暴露 validation 48。158 篇资料、220 个原始正文 Chunk、问题及语料指纹、模型 digest 逐轮一致，运行代码为干净提交 `5fa9eb4bb8c013b09ef011b5cacc9d32eb5a187c`。题目与答案未因结果修改。

固定 `nomic-embed-text`、plain 编码、CJK 分词、1000/150 分块、最终 Top 5 及现有规则重排。正文基线和上下文基线的向量输入不同；三种上下文策略之间的向量输入相同，仅关键词策略不同。没有比较新模型、查询扩展或修改重排与回答生成。

```bash
pnpm --filter @knowbase/api benchmark:retrieval \
  --python "$PWD/.venv-rag-eval/bin/python" \
  --suite recall --dataset benchmarks/knowbase-recall-v3 \
  --split all --encoding plain --lexical cjk \
  --context title-heading --keyword-policy body-reserve \
  --route-budgets 10:10,15:15 \
  --output-dir reports/retrieval-body-protection-body-reserve
```

其余轮次使用 `body/combined`、`title-heading/combined`、`title-heading/weighted`，并分别设置输出目录。索引原始读取上限为各路保留预算的三倍、最多 100；`body-reserve` 会进行两次关键词索引查询，每次使用相同上限。每个预算实际执行检索，未从大预算结果离线裁剪。

## 两种修复方式

`weighted` 用一次 `best_fields` 查询分别计算 `content^2` 与 `retrieval_text`，tie_breaker=0.1。正文词频与长度统计独立于辅助文本；辅助字段包含标题、章节和正文，并非仅标题字段。

`body-reserve` 并发查正文和辅助文本，重复按“两条正文、一条辅助”选择唯一 Chunk，不足则回填。同一 Chunk 不重复占位，保留被选中命中的原生分数。之后复用版本、发布状态、权限复查与保留预算裁剪。任何一路索引请求失败都报错，不伪装为空召回。策略与纯候选选择位于独立工具模块，Elasticsearch adapter 负责外部读取。

固定混合预算只能预留一部分正文位置，**不能数学上保证保留所有原正文候选**；15 条预算的结论来自本轮逐证据回归，不能推广为任何语料都不退步。

两种修复在 15:15 下，跨三个分组逐证据比较，均没有丢失正文基线或标题章节基线已经命中的池证据；开发标题依赖题均为 100%。原始索引中的标注证据全部存在，合并阶段损失为 0。旧题池证据仍为 96.53%，原本就没命中的证据仍需继续排查，不能称整个召回层已达到 100%。

## 已知旧题的具体变化

- `val009`：上传成功与检索可见之间还差什么。此前辅助字段的关键词排名受标题影响而下降，被保留预算截掉。正文基线池证据为 100%，上下文 combined 在 10/15 均丢失；weighted 与 body-reserve 在两个预算均恢复。所有配置最终 Top 5 对此题的证据召回仍为 0，说明候选恢复之后还有选择层损失，本轮未修改选择层。
- `val029`：修订相关多证据题。正文基线在两个预算均完整命中；上下文 combined 和 body-reserve 在 10 条预算仅命中一半，15 条恢复完整；weighted 在两个预算均完整。因此 15 条是本轮候选配置的必要部分，不能单独宣传策略而省略预算。

完整逐证据差异在结果 JSON 的 `pool_evidence_changes` 中，证据下标对应冻结问题的原始标注顺序。这里只宣称池证据没有新增损失，不宣称每道题最终选择都不退步。

## 成本、检验与使用边界

body-reserve 的关键词索引请求从一次变为两次。15 条预算下，每个子查询最多读取 45 条，两次合计最多 90 条，再合成为最多 45 条交给应用复查并保留最多 15 条；向量保留仍为 15，最终仍为 5。候选原生分数没有跨字段标定，因此最终选择质量必须一起观察。一次固定顺序串行计时不足以证明并发吞吐或生产 P95，也不能因为某次测量更快就宣称两次查询更省成本。

API 单测 230 项、真实 CJK 索引一致性 18 项、前端单测 11 项、Node 工具测试 17 项、Python 检索测试 22 项、适配器测试 11 项通过。真实索引测试覆盖两种策略的活跃批次、草稿隐藏、允许文档范围、空结果和原文返回；单测覆盖查询序列化、去重回填及部分请求失败。API/前端构建、变更文件格式、Compose 配置与空白检查通过；前端保留既有包体积提示。索引一致性第一次运行在基础设施 before-hook 等待超时，未通过计分；保留失败日志后同代码完整重跑 18 项通过。投递代码本轮未变，未重跑独立 RabbitMQ 投递可靠性测试。临时容器与卷均清理。

这仍是助手合成、存在模板相关性且已全部暴露的 224 题。负样本候选池空结果率为 0，不代表系统正确拒答；本轮没有测答案正确率、幻觉或拒答。后续需要未参与调参的问题与实际负载来确认泛化和成本，不能宣布生产或整个召回层验收。

如采用候选配置，设置 `RAG_RETRIEVAL_CONTEXT=title-heading`、`RAG_KEYWORD_POLICY=body-reserve`、`RAG_KEYWORD_ANALYZER=cjk`；最终 TopK=5 的现有 3K 策略对应 15:15。切换上下文或为旧记录启用 CJK 必须先完成受控重建与协调查询切换，步骤以 [检索指南](../../../docs/retrieval.md)为准。已完整使用相同上下文和 CJK 索引时，仅更改关键词策略无需重算向量。本轮不自动更改默认值或业务环境。
