# 多意图查询拆解对照

本轮结论：**不采用这版规则拆解，保留 `off`。** 固定候选预算后，两种拆解模式都没有增加任何池证据，剩余审核题也没有找回。只拆关键词导致一道开发题最终证据丢失；两路都拆虽然让部分题目的最终选择改善，但仍有相同退步且请求成本更高。按照事先冻结的停止条件，不继续针对已测题微调。

这不说明所有多意图检索都无效，只说明本轮“原问题＋两个原文子句、固定预算与交替选取”的具体方案没有足够收益。没有接入业务查询，没有改分块、索引内容、跨路融合、重排、回答生成或默认配置。

## 冻结范围与实现

[协议](multi-intent-protocol.json)与实现先提交为 `17482e88de11f5c8a2973a6d12d88b23a1d003d8`，测量时工作区干净；[结果 JSON](multi-intent-results.json)保存全部汇总、逐证据损益、剩余失败、子查询计划与请求计数，[决策 JSON](multi-intent-decision.json)记录不采用的依据。

3 种模式各测全部 224 题，共 **672 次计分 IPC 请求**，不含预热与原问题 HTTP 抽查。每轮使用全新隔离索引，158 篇文档、220 个原始正文 Chunk、问题/语料指纹和模型 digest 逐轮核对一致。固定 nomic-embed-text/plain、CJK、标题章节上下文、body-reserve/2:1、1000/150、关键词 30、向量 15 和现有 Top 5。所有问题都是助手合成、存在模板相关性且已经暴露，不构成真实用户或未见验收。

规则仅在恰好两个片段各至少六个字符、各有问句标记时提取子句；只按引号/括号外的中文逗号、分号与问号切分，包含反引号、超过 512 字符或引号/括号不闭合时回退原问题。保留原问题，不调用模型、不插入术语、不改写否定、数字与条件。规则在旧题 12、开发 24、已暴露验证 12，共 48 题触发；其余题仍走原查询。它不是人工标注的多意图分类器，未证明覆盖所有复合问题。

例如 `val017` 被提取为：

```text
原问题：解析尚未成功的草稿能申请发布审批吗，最终由什么角色批准？
子句一：解析尚未成功的草稿能申请发布审批吗
子句二：最终由什么角色批准
```

提取原文字面并不能保证子句独立完整：后半句可能缺少共享业务主体或前半句的条件。保留原问题只能提供另一条路径，不保证这种上下文损失被自动修复。

## 总预算与职责边界

关键词调用预算按原问题/子句一/子句二分为 15/8/7；现有服务分别读取 45/24/21，合计最多 90 条，body-reserve 的两次实际关键词查询读取合计仍最多 180 条。向量调用预算分为 8/4/3，读取 24/12/9，合计最多 45 条。最终路由保留上限仍为关键词 30、向量 15，并非每个子查询各保留 30/15。

各分支调用原有 `RagQueryService.recall`，传入相同用户、各自执行版本/发布状态/可见范围复查。仅在单一路由内部按“两条原问题、一条子句一、一条子句二”选择唯一 Chunk，不足回填，保留选中命中的原生分数。只从复查合格候选选择；任何分支失败或缺少完整合格候选诊断时整体报错。分支重叠会减少实际唯一候选数，不补发额外查询。

跨关键词/向量的 Chunk 合并与最终规则完全复用，重排仍输入原问题。拆解/预算计划和召回编排位于独立评测模块；公开 HTTP 没有拆解模式或调试端点。HTTP 一致性只抽查原问题、现有 15:15 路径，不能据此宣称拆解已通过业务 HTTP 验证。

本轮 off 与上一轮 30:15 的池证据逐条一致。两种拆解相对 off 的**池证据获得和丢失都为零**，不只是平均分相等。所有配置的原始索引标注证据存在率为 100%，跨路合并损失为 0。`val017` 在两路当前原始候选中仍未命中，三种模式的池证据都为 0，未解决目标失败。

最终选择的逐证据差异：

- 只拆关键词：`v3_contract_06`（合同用印撤销时间及起算点）丢失证据下标 0；没有其他最终证据收益。
- 两路都拆：同样丢失 `v3_contract_06` 的证据下标 0；`val036`、`v3_equipment_09`、`v3_travel_09` 各获得下标 1，已暴露组 `v3_sample_09` 获得下标 0。这些证据原本已在池中，因此属于候选组成/分数变化造成的最终选择副作用，不属于新增召回证据。

证据下标沿用冻结问题标注顺序，从 0 开始。两路都拆的开发平均分虽然相同，仍包含“两题改善、一题退步”，不能宣称逐题不退步。后续没有为修复这道题再调整拆解条件或配额。

以下仅统计 224 次计分问题的实际计划调用数，不含预热与 HTTP 抽查；索引请求数按每次关键词 body-reserve 两查、向量一查计算。

| 模式            | 关键词召回调用 | 向量召回/问题 Embedding 调用 | 索引查询请求合计 |

| clauses-both    |            320 |                          320 |              960 |

两路都拆的索引请求增加约 42.9%，问题 Embedding 调用增加约 42.9%；各路可见范围和元数据批量复查也随分支调用增加。固定读取条数上限不等于固定 CPU、模型或数据库成本，不能把本轮称为等成本比较。

三轮固定顺序、每种仅一次串行测量，不能得出生产延迟结论。两路都拆的开发/旧题/已暴露组 P95 分别约 370/343/2012 ms；off 约 178/161/210 ms。只拆关键词的本次耗时较低不能证明它稳定更快。内部 trace 的分支阶段耗时为工作量求和，路由 elapsed 是并发墙钟耗时，两者不能混作同一指标。

## 复现与检验

```bash
pnpm --filter @knowbase/api benchmark:retrieval \
  --python /path/to/evaluation-venv/bin/python \
  --suite recall --dataset benchmarks/knowbase-recall-v3 --split all \
  --encoding plain --lexical cjk --context title-heading \
  --keyword-policy body-reserve --body-slots 2 \
  --query-mode off --route-budgets 30:15 \
  --output-dir reports/retrieval-multi-intent-off
```

另外两轮只更改 `--query-mode clauses-keyword|clauses-both` 和输出目录。安装评测 requirements，并使用同一已安装的模型；本轮没有改模型或任务前缀。模式、子查询预算与语料元数据需要匹配，模式不一致会拒绝计分。

Node 24、Python 检索 24、适配器 11、API 232、前端 11 项通过；API/前端构建、变更格式、组合 Compose 与空白检查通过，前端保留既有包体积提示。新增测试覆盖原文提取、否定与数字、引号和代码回退、1..100 预算上限、去重回填、身份透传、分支失败、诊断完整性、模式计分一致性及 HTTP 原路径抽查。三轮全量真实索引评测成功并清理临时容器与卷。应用索引与投递实现未变，本轮未重跑独立索引一致性/投递故障注入套件，其此前通过记录见候选边界报告。

本轮保留内部实验工具和可复核的失败结论，业务默认继续不拆解。没有未见问题与人工候选相关性标注，不能据池证据相同宣称检索精度提高，也未评估生成、幻觉或拒答。
