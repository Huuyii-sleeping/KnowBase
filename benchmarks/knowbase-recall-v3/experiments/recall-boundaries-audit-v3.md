# 候选截断、正文比例与预算对照

本轮不再细调正文比例，保留默认 2:1。实验候选预算从关键词 15 / 向量 15 调整为 **关键词 30 / 向量 15**：旧题池证据召回从 96.53% 升到 98.61%，找回两题的三条证据，开发与已暴露验证池证据保持 100%。逐证据对照未出现新增池证据或最终选择损失，但最终 Top 5 指标没有提高。该预算目前由评测 CLI / 内部诊断支持，业务 HTTP 仍使用既有 3K 等额预算，本轮没有部署或改默认值。

## 定位与实现

此前 `filtered_or_route_budget` 无法区分安全复查和数量截断。`RagQueryService.recall` 现在在同一次批量元数据复查之后保留 `eligibleCandidates`，再裁剪路由预算；不增加数据库查询，也不放宽发布状态、版本或权限规则。公开 HTTP 返回不包含诊断字段。

评分工具为每条损失记录两路的原始、合格、保留排名，并区分：

| 阶段                  | 含义                                                       |
| --------------------- | ---------------------------------------------------------- |
| not_in_raw_candidates | 当前读取范围中没有正确证据；不等于索引里根本不存在         |
| metadata_filter       | 原始候选命中，但没有通过当前发布状态、可见范围或修订号复查 |
| route_budget          | 已通过复查，仍被保留数量截断                               |
| merge_loss            | 路由保留后在合并中丢失                                     |
| selection_loss        | 已进入池，但未被原规则选进最终结果                         |

旧 trace 不包含合格阶段时保留模糊归因，不追溯猜测过滤原因。缺失/不可见文档不通过额外越权读取区分具体原因。归因和证据排名是独立 Python 工具，查询策略与候选编织是纯 TypeScript 工具，索引 adapter 继续负责 Elasticsearch；没有增加跨职责服务。

正文比例使用 `RAG_KEYWORD_BODY_SLOTS=1|2|3`，默认 2，对应每取一条辅助候选之前取几条唯一正文候选。CLI 对应 `--body-slots`；去重、回填与原生命中得分规则不变。

## 具体找回了什么

| 问题                                     |      原始/合格关键词排名 | 15:15                | 20:15      | 30:15              |
| ---------------------------------------- | -----------------------: | -------------------- | ---------- | ------------------ |
| val006：开放范围与空权限默认值           |                  18 / 18 | 两条证据都被数量截断 | 两条都找回 | 两条都保留         |
| kb027：完整正文存储与向量索引            |  25 / 25（正文存储证据） | 丢一条存储证据       | 仍丢该条   | 存储与索引证据完整 |
| val017：解析未成功能否提交审批、由谁批准 | 两路当前原始候选均未命中 | 未找回               | 未找回     | 未找回             |

前两题确认为预算截断，并非权限或修订过滤。被找回的证据随后仍未进入最终 Top 5，损失从 `route_budget` 转为 `selection_loss`；本轮没有改重排或把池召回当作答案正确率。

## 无效方向与停止条件

1:1 与 3:1 相比 2:1 都没有新增池证据。1:1 还丢失 `v3_contract_05` 的一条最终证据；3:1 的最终证据也没有提升。因此停止比例细调，保留 2:1，不根据旧题反复微调。

关键词预算只测到协议指定的 30，之后不再为 val017 继续增加数量。该题需要另查术语/匹配问题；“未进入当前原始候选”不能直接归因成模型完全不理解。原始关键词读取上限也随保留数从 45 增至 90，这是本轮成本与诊断的一部分。

对“审批”与“审核”的探索结论及实验边界在下节记录。单题、已暴露问题上的探查不能替代整套术语扩展回归；没有把业务术语映射硬编码进生产代码。

## 简单术语追加没有解决剩余问题

完整 API 术语探查两次未完成后，使用独立临时 Elasticsearch、相同生产映射与 `RagChunkTextService` 重建全部语料。逐一核对 220 个原始正文 Chunk 与先前评测完全一致，全部 bulk 完成且刷新后才查询。[探查 JSON](approval-term-probe.json)保存语料指纹、分词和排名；它没有向量、应用权限/版本复查或最终选择，只用于分析关键词匹配，不纳入前述 1120 次计分。

| 查询             | 原始正文排名 | 标题章节辅助字段排名 | 关键词保留 30 是否命中 |
| ---------------- | -----------: | -------------------: | ---------------------- |
| 原问题           |          174 |                  175 | 否                     |
| 原问题追加“审核” |          162 |                  162 | 否                     |

“审批”与“审核”产生不同的 CJK 词项，但补一个同义词仍远不足以进入每个子查询前 90 条，因而没有解决问题。这个方向本轮停止，不上线单题驱动的术语替换，也不继续提高预算去覆盖第 162 条。数据表明还有较强的匹配干扰，不能仅凭同义表达就认定缺失原因已完全找到；下一项值得独立冻结测试的是多意图问题拆解/干扰词分析，而不是继续微调同一个扩展词。它仍是后续候选方向，尚未实现或宣称有效。

## 成本与复现

30:15 的关键词仍查询两次，每次最多读 90 条，共最多 180 条；合成为最多 90 条供元数据复查，保留最多 30 条。向量仍最多读取 45、保留 15，合并池去重前最多 45 条。旧题平均池大小由 26.84 增至 39.98；增加了索引读取、候选处理与后续选择成本。

每轮只有一次固定顺序串行测量，第一轮的耗时波动明显高于后两轮。不能据此宣称扩大预算更快，或比例改变提高了生产吞吐；尚未证明生产负载下的成本可接受。收益集中在两道已知旧题，未见数据上的价值仍需验证。

```bash
pnpm --filter @knowbase/api benchmark:retrieval \
  --python /path/to/evaluation-venv/bin/python \
  --suite recall --dataset benchmarks/knowbase-recall-v3 --split all \
  --encoding plain --lexical cjk --context title-heading \
  --keyword-policy body-reserve --body-slots 2 \
  --route-budgets 15:15,20:15,30:15 \
  --output-dir reports/retrieval-boundaries-slots2
```

另两轮分别用 `--body-slots 1` / `3`、`--route-budgets 15:15` 和独立输出目录。环境安装仓库 `tools/rag-evaluation/requirements.txt`。没有更换模型、增加新向量编码或重新调整最终选择。

## 验证与交付边界

API 232 项、真实 CJK 索引一致性 20 项、前端 11 项、Node 17 项、Python 检索 24 项、适配器 11 项通过；API 与前端构建、变更格式、组合 Compose 配置和空白检查通过。前端仍有既有包体积提示。新增测试覆盖三种比例、非法输入、元数据/预算分界、旧 trace 兼容、诊断完整性以及公开响应不泄漏原始/合格候选。真实索引检查覆盖三种比例下的活跃批次、文档范围与草稿隐藏。

索引一致性首次初始化 before-hook 超时、未执行到业务断言，同代码重跑全量 20 项通过。完整 API 术语探查另有镜像仓库 TLS 超时与隔离 API 请求超时，均不纳入计分；本轮主要矩阵三轮均完整成功。诊断预算与比例代码已提交，业务默认比例仍为 2，默认正文/combined/standard 与 HTTP 3K 路由规则不变。投递代码未变，独立 RabbitMQ 可靠性测试本轮未重跑。

本轮临时评测、失败探查与关键词探查的容器和卷均已清理；本地原有业务容器没有删除。
