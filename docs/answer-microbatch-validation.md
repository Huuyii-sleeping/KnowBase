# BGE 长度分组与微批处理对照

2026-11-23 至 24 日，用户选择暂不采用 12 秒队列，先测试跨请求微批处理。本轮只在本机忽略目录中实验，业务默认、用户配置和运行中的主项目均未改动。

## 方案与范围

直接合批并不会减少实际窗口数量。现有 BGE 对单请求的窗口已经按 8 个一批推理，因此先比较原串行、跨请求合批 8 和合批 16；再比较单请求内部按长度分组、跨请求按长度分组 8/16。长度分组将相近长度窗口放在一起以减少 padding，评分后恢复原窗口、候选和请求顺序，仍完整覆盖正文并取候选各窗口最大分。没有截断、改模型、改精度、改最终选择规则或按题目标签调度。

固定池来自前一轮同一索引、单并发立即回退模式的全部 32 道题，689 个候选、859 个正文窗口，每请求 18–33 个窗口。每四个请求一组，各方案跑两遍；逐组轮转顺序，第二遍反转。不涉及 DeepSeek。来源为已暴露合成回归题，不能当作真实用户独立验收。

两组共 448 次请求评分。每个候选方案均与本组原串行逐请求比较 1,378 个分数，两遍分数完全一致，最终成员和次序均未变化；仅说明这批输入，没有证明任意 FP16 输入都严格相等。batch 8 长度分组的补齐后 token 从 208,653 降到 135,712。不同时间运行的两组基准耗时本身不同，不能跨组相减宣称加速；这些是整体推理耗时，不能直接当成单请求或完整问答延迟。

跨请求长度分组比单请求内部长度分组再减少约 9.0% 的总推理时间，但合批请求通常共同等待结果，先到请求未必更快。直接合批和增大到 16 没有更好收益，不采用这两个方向。

## 真实 HTTP 与实验准入

微批适配器允许最多 8 个在途评分，每批最多 4 个请求，最多收集 10 ms；总窗口最多 4,096、单请求仍最多 512。只有一个 GPU 推理线程。原 API 的单请求在途门槛会阻止跨请求合批，因此实验为每个获准请求提供独立的在途状态，共享故障冷却，再调用原 `HybridRerankService`；评分传输、规则回退、模型结果验证和 `selectBge` 仍使用原实现。这里改变了准入，不能声称是完全未改调度的生产运行。

串行对照仍使用上一轮 12 秒、最多 7 人等待的队列；另外加入同一队列加单请求长度分组，区分分组收益与跨请求收益。所有方案保持 20 秒评分 HTTP 期限与生成模型配置。

首次完整问答计划 288 次，运行到 124 次时累计 9 次生成阶段失败，触发提前停止，未执行的 164 次不计为成功。失败发生在约 5–27 秒，含 `Error` 和 `TimeoutError`，没有服务端诊断，不能断言是微批引起。BGE 评分均完成。所有 124 次有同请求 Trace，106 次 BGE 选块与原选择函数完全一致，18 次规则回退与原规则逐字段一致。实际处理了 40 个微批请求、28 个批次，其中 6 批包含 3 个请求，其余单请求，证明确实发生跨请求推理。

单并发两种方案各 16 次，均为 8/8 完整回答、8/8 正确拒答。4 并发实际执行：原立即回退 21/24 完整（两道误拒、一次调用失败）；原队列只执行到 20 题，20/20 完整；单请求长度分组队列 21/24 完整（三次调用失败）；微批 19/24 完整（五次调用失败）。分母不齐，不能据此排序方案。309 条返回引句均在相应来源，语义复核未发现其他错答。

## 中断与传输诊断

第一次仅重排 HTTP 补测在电脑休眠期间出现约 300 秒等待，系统日志记录 `Idle Sleep` 后接 `Thermal Emergency Sleep`。该轮原始记录保留，不作为性能结论。后续使用有期限的临时防休眠，仅阻止空闲休眠，不屏蔽系统过热保护。

唤醒后的对照完成全部 4 并发：每方案 32 次均评分成功、分数和最终选择与固定池原串行一致。原队列、单请求长度分组队列、跨请求长度分组的 P95 分别为 6.95、5.51、5.59 秒。8 并发首波微批出现两次立即发生的 `ECONNRESET`，故按预设条件停止。

独立小输入探针在原 HTTP 监听 backlog 5 下连续三轮各有 2/8 连接重置；仅将实验运行时监听 backlog 调到 16 后，原样三轮 24/24 成功。应用连接上限仍为 16、评分在途仍为 8，没有增加 GPU 并行推理。该修正未写入生产代码，之后的 8 并发补测单独保存，不覆盖失败轮次。

## 决策与交付边界

**本轮不采用跨请求微批处理，也不切换原业务默认。** 直接合批没有提速；长度分组的收益明确，但跨请求相对单请求内部长度分组的额外收益较小，完整问答也没有表现出稳定优势。不能把一次生成失败集中现象当作微批必然不可靠，但当前证据不足以支持为它增加集中调度复杂度。

下一步优先将**单请求内部按窗口长度分组**做成小而独立的推理优化，沿用原评分/选块合约，再验证原并发准入。注意本轮该方案的完整问答结果是在 12 秒队列下测得：只接入长度分组并不能保证所有并发请求都能使用 BGE，也不能承诺直接获得本表完整率。队列的等待取舍尚未被用户采纳，本轮不借性能优化自动将队列变为默认。

基础实验的 9 项测试覆盖请求/候选身份隔离、末尾窗口、最大值聚合、非法输入/超限、非有限/不完整分数、推理异常恢复、长度排序还原、单推理所有者、满员/等待到期/取消及关闭。原运行时 12 项测试通过。没有新增业务模块，不重复无关全量构建；生产接入仍须完善整链路取消、关闭、期限与可观测性。

隔离 API、容器、卷以及本轮两次启动的临时 BGE 均已清理，临时防休眠随测试进程结束释放；用户原有 Ollama 未动。所有协议、指纹、分数、Trace、失败和运行器位于忽略目录 `reports/answer-microbatch/2026-11-23-r1/`，实验文件和密钥不进入正式提交。前序结果分别见[并发基线](answer-concurrency-validation.md)和[队列对照](answer-queue-validation.md)。

## 单请求长度分组的正式落地

2026-11-24，用户批准优先落地单请求内部长度分组。正式运行时已默认采用该计算顺序，设计合约以[BGE 重排设计](rerank.md)为准；没有增加配置开关，原并发准入保持原样，队列和微批仍未接入。更新后需重启 Python 运行时才能使用新代码，无需重建索引。

正式代码与改动前 Git 版本在同一份权重上交替执行 32 题两遍，第二遍反转题序与执行顺序，共 128 次评分。64 对请求的 1,378 个候选分数完全一致，正文窗口诊断、最终选块成员及次序均不变。原版本评分总耗时 213.42 秒，新版本 163.00 秒，减少约 23.6%；单次评分 P50 从 2.80 秒降到 2.10 秒，P95 从 6.40 秒降到 4.76 秒。正式 HTTP 接口另有两次真实模型请求，身份、候选和分数均验证通过。

耗时包含窗口准备与推理，不代表完整问答加速比例。共享主机存在负载波动，运行前段与构建及回归测试有重叠；保留全部样本，没有据此调参数或只选最快运行，仍以配对结果和原文/分数一致性为主要依据。来源继续是已暴露合成题，不能保证所有 FP16 输入在改变批次补齐后都逐位相同。

新增纯批次规划函数及独立测试，模型适配器只增加下标还原和每批数量检查；不涉及存储。16 项 Python 测试覆盖稳定同长度次序、尾批、跨候选还原、窗口超限、无效/不完整分数及失败后恢复，全部通过；API 的 73 个测试文件、394 项测试、构建及 Nest 模块接入检查通过。文档格式与变更检查通过，实验进程已退出。原始复测记录位于忽略目录 `reports/answer-length-batching/2026-11-24-r1/`，不进入正式提交。
