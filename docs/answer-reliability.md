# 问答期限与模型故障处理

问答使用统一的失败类型、整次期限和有限传输恢复。目标是使临时故障有一次恢复机会，同时让调用方区分服务失败与知识不足。正常答案、提示词、来源校验、模型选择和 BGE 并发准入均沿用原合约。

## 调用与职责

`AnswerService` 在一次问答的异步上下文中建立期限，协调检索、上下文、生成和引用；`answer-execution` 保存该请求的期限、阶段及调用计数，不与其他请求共享重试名额。`model-transport` 负责单次调用取消和有限恢复，`model-failure-classifier` 将 SDK 状态/连接错误转换为固定的安全类别。`chat-model-invocation` 只提取最终文本、检查完成状态；来源结构修正继续由 `AnswerGenerationService` 负责。

控制器的 `AnswerFailureFilter` 只映射已知业务失败为 HTTP，不将内部异常一概当作模型故障。检索自己的异常仍沿用现有错误路径；检索迟迟不返回则受整次期限约束。模型密钥、Base URL、原始错误响应和文档内容不会出现在该失败响应中。

## 时间预算

整次问答默认 45 秒，覆盖检索、上下文、模型调用、传输等待和一次引用修正。模型每次仍最多 30 秒；第二次调用不能另起一个完整的问答预算。例如检索已经用掉 20 秒，生成与可能的修正共用剩余约 25 秒。45 秒是本轮选择的工程上限，并非根据真实用户延迟分布确定的最优参数，没有新增环境配置开关。

总期限到达时，API 结束等待并将取消信号传给正在执行的生成调用。每个主要阶段后都复查期限，迟到的检索结果不会触发生成，迟到的生成结果不会发布为成功。计时器和取消监听在正常完成或失败后清理。

该期限不能中断已进入 PyTorch 的 BGE 推理，也未向数据库、索引及图谱驱动全面传递取消信号；已经开始的检索可能继续到其自身结束。JavaScript 计时器依赖进程正常调度，电脑休眠、事件循环长时间阻塞时不承诺精确墙钟上限。取消生成也不保证上游立即停止计算或计费。当前没有新增客户端断开取消或服务端关闭时的全链路清理。

## 有限恢复

SDK 自动重试仍为零，由应用明确控制：

- 429、502、503，以及识别到的连接重置/连接拒绝/临时 DNS 或 socket 故障，允许最多一次额外传输调用。
- 整次问答共用一个恢复名额，包括引用修正阶段；正常最多两次内容调用，因此加入传输恢复后最多三次实际模型请求。恢复仍使用当前调用的同一提示与证据，不改答案内容。
- 默认随机等待 250–500 ms，避免多个失败请求固定同时重试。若上游给出有效 `Retry-After`（秒数或 HTTP 日期），至少等待其指定时长；需要等待超过 2 秒或等待后不足 5 秒剩余预算时，直接明确返回失败，不开始恢复。
- 单次超时、总期限耗尽、401/403、400/404、普通 500、未知错误、空输出、截断或非文本回答均不自动重试。普通 500 暂未列入自动恢复白名单，防止不明确的服务端错误重复执行。

没有无限重试、重新排队或切换到另一个模型。第一次调用可能已被上游处理，重发存在额外计费可能；对已经超时的生成不自动重复，只对上述有限类别恢复。故障分类的 `transient` 只控制应用自动恢复，HTTP 的 `retryable` 表示调用方之后是否适合重试，两者不等价。

## HTTP 合约与用户反馈

成功回答、知识不足及冲突继续返回原有正常结果。服务失败使用以下非成功 HTTP 响应，不带 `answer`、知识不足状态或伪造引用：

| code                        | HTTP | 提示                                   | retryable |
| --------------------------- | ---: | -------------------------------------- | --------- |
| `ANSWER_TIMEOUT`            |  504 | 本次问答超时，请稍后重试。             | true      |
| `MODEL_TIMEOUT`             |  504 | 回答生成超时，请稍后重试。             | true      |
| `MODEL_RATE_LIMITED`        |  503 | 问答服务繁忙，请稍后重试。             | true      |
| `MODEL_UNAVAILABLE`         |  503 | 问答模型暂时不可用，请稍后重试。       | true      |
| `MODEL_CONFIGURATION_ERROR` |  503 | 问答模型配置异常，请联系管理员。       | false     |
| `MODEL_INVALID_RESPONSE`    |  502 | 模型未返回完整有效的回答，请重新提问。 | false     |
| `MODEL_OUTPUT_LIMIT`        |  502 | 回答超出长度限制，请缩小问题范围。     | false     |

响应 JSON 包含 `statusCode`、`code`、固定中文 `message`、`retryable`。有效等待提示通过 `Retry-After` 响应头传回，向上取整到秒，最大显示一天。现有前端直接显示后端 `message`，无需修改问答内容或将这些错误插入助手答案。

## 基础观测

失败时，无论 Langfuse 是否启用，本地结构化日志均记录固定错误类别、失败阶段、耗时、实际模型调用数及传输恢复数，不记录问题、密钥和模型原始错误内容。启用 Langfuse 时，同样记录这些字段；成功记录补充恢复次数和此前失败类别。生成记录名称改为通用 `generation.answer`，避免 DeepSeek 继续显示为 Ollama。

这里不是完整线上观测交付：尚未补齐每路 BGE 降级原因、所有调用 token 用量或全链路指标看板。该部分与后续持续负载验收另行处理。

## 验证

使用本地随机端口的 OpenAI 兼容故障服务，经过真实 SDK、真实 `AnswerService`、来源校验以及 Nest 问答 HTTP，测试临时 503/短 429/连接重置恢复、持续异常的次数上限、长 `Retry-After`、401、500、504、空输出/截断、固定错误响应与正常拒答。外部知识库检索使用小型 fixture，不需要真实 DeepSeek Key，不向外发送业务资料。

假计时器测试验证 30 秒单次期限、45 秒整次期限、引用修正共享预算、剩余时间不足不重试、迟到结果不继续后续阶段及计时器清理；并发异步上下文测试验证不同请求的恢复名额独立。故障恢复能改善的是可恢复调用的成功机会，不提高模型本身的语义理解，也不能据这些可控样本推断真实 DeepSeek 的故障率或费用。

本轮检查：API 78 个测试文件、443 项测试，Web 11 项测试，Node 评测工具 49 项、Python 重排运行时 16 项均通过；前后端构建、三份隔离 Compose 合并配置、修改文件格式、本地文档链接与差异检查通过。前端构建保留既有的大包提示。13 项真实 SDK/Nest HTTP 测试均使用本机故障服务，不能计作 13 次真实 DeepSeek 请求或线上成功率。实现验证期间没有修改用户 `.env` 或重启主服务；后续提交与部署进度统一记录在[迭代执行路线](rag-iteration-roadmap.md)。
