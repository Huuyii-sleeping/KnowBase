# 回答遗漏、比较误拒与长答案修复

2026 年 11 月 23 日，根据[新来源验收](answer-acceptance-validation.md)的失败案例，采用通用任务核对提示、26,000 字节完整输入预算和 4,096 token 输出上限。保留原模型、结构化合约、逐字引句校验、一次格式修正及 30 秒单次期限。当前设计以[问答上下文](answer-context.md)为准。

## 原因与修改

| 问题               | 定位                                                               | 最终修改                                                                                           |
| ------------------ | ------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------- |
| 代领材料遗漏       | BGE 已将基本材料及附加材料完整交给生成模型，模型只回答“还须”的材料 | 来源之后追加任务核对：逐个回应子问，合并基本要求与附加要求，必答项必须写入结论文本，不能只放进引句 |
| 分别列值误拒       | 模型把两份资料数值不同直接当成不能回答                             | 核对用户要分别陈述还是裁定唯一规则；前者逐份引用，后者在缺乏优先依据时才判为冲突                   |
| 十二项长规则截断   | JSON、结论及原文引句共同消耗输出预算，1,024 token 不够             | 输出上限提高为 4,096；继续拒绝截断结果，不补闭合括号或展示半截答案                                 |
| 新提示挤占证据空间 | 追加约 1.3K 字节指令后，原来接近 24K 的输入会整块放不下            | 输入上限提高到 26K 字节，仍包含修正指令、问题和来源元数据，不截断正文；近上限探测通过              |

没有增加在线审查模型、关键词清单或文档专用判断，也没有改变召回和重排。提示词只是引导模型完成任务，代码仍不能证明任意答案语义完整。

## 对照与丢弃方案

先冻结 84 份定向输入：前轮 48 题、两条 HTTP 失败的正反顺序重复共 8 次、六组新主题的材料/比较/唯一选值/未知信息共 24 题，以及 4 道长规则题。随后单独冻结近输入上限与重复探测；最后用 156 道历史回归和上述输入组成 248 次业务模块回归。全部题目、来源和输出保留，没有修改标注来提高分数。同作者合成题及重复请求不能当作独立人工盲测。

本轮旧提示的 84 份对照再次出现两条比较误拒和两条代领材料遗漏。追加完整任务核对后，这些定向问题未再复现；仅加输出预算的历史与定向复测仍有比较误拒，说明扩大输出上限不能代替语义处理。

几种替换或精简原有规则的提示也能补齐材料，却在长上下文探测中出现误拒，并有比较题退步；在来源后重复问题也没有稳定解决。均丢弃。最终保留原规则，追加完整核对提示，并验证输入预算补偿，不把实验选项留在生产配置中。

首轮实验错误地只修改 LangChain 外层对象的 `maxTokens`，其内部 Chat Completions 实例仍发送 1,024；该轮所有所谓 4,096 上限结果均不作为预算对照证据。随后检查实际 `invocationParams().max_tokens` 并重新运行，最终编译业务适配器也通过实际传输参数测试。原始错误实验保留，不覆盖。

## 最终实际业务模块回归

最终不使用实验提示类或请求参数覆盖，执行编译后的 `AnswerService → AnswerContextService → AnswerGenerationService → ChatModelService`，真实调用用户配置的 DeepSeek Flash，再执行结构与引句校验和引用映射。只有检索结果及观测存储用替身；不是重新执行上传、发布和检索的完整 HTTP 验收。

| 分组                    | 请求数 | 结果                                                                                    |
| ----------------------- | -----: | --------------------------------------------------------------------------------------- |
| 历史回归                |    156 | 94 次 answered、62 次安全拒答；状态符合历史标注。复核发现一题存在既有完整性问题，见下文 |
| 前轮新来源集            |     48 | 30/30 完整回答且引用支持，18/18 安全拒答；上轮固定候选为 29/30 和 18/18                 |
| HTTP 失败候选回放       |      8 | 代领材料和分别列值两题，各含正反顺序及重复；8/8 完整回答，基本材料不再遗漏              |
| 新主题配对题            |     24 | 12/12 完整回答，12/12 安全拒答；没有把唯一选值或未知手续费强行回答                      |
| 4/8/12 项与十二项长规则 |      4 | 4/4 必答项完整；最长回答消耗 1,857 输出 token，约 6.28 秒，原先在 1,024 处截断          |

248 次最终调用没有传输异常或格式重试；309 份返回引句均在对应来源正文中，来源及引用映射一致。历史组流程 P50/P95 约 0.90/1.85 秒，新来源组约 1.10/2.30 秒。远程负载和缓存影响延迟，不据此宣称稳定提速。4,096 是上限，短回答并不会固定用满，但更长实际输出可能增加延迟和费用。

历史题 `reg-kb006` 询问 PRIVATE、TEAM、PUBLIC 的含义及空权限处理，模型仍只列三个枚举及默认 PRIVATE，没有展开权限含义。与上一轮保存答案相同，属于既有回答完整性遗漏；因此历史组只能称状态符合标注，不能据此宣布 94 道有答案题全部完整正确。该发现保留为下一轮清单型解释问题的回归，不把状态通过等同于质量通过。另有历史 429 重试题标签歧义，沿用原标签，前轮已说明。

## 失败、边界与工程检查

实验阶段发生过模型超时和连接失败，含一轮 248 次对照中 34 次传输异常，采用前方案复测中 4 次超时；未将其当作知识拒答或用重跑结果覆盖。最终 248 次成功只说明该轮情况，不证明托管服务稳定性保证。

输出仍有 12 条结论及 4,096 token 上限，输入仍有限，单次期限仍为 30 秒；超限或服务故障继续显式失败。这次没有实施无限重试、自动分批长答案、在线语义证明，也未重新验证本地 Ollama 模型的实际质量或完整 HTTP 并发。

生产改动只涉及任务提示与预算，职责没有扩大：上下文负责选择和输入预算、适配器负责请求与期限、纯函数负责输出校验、生成服务负责一次格式修正。没有新持久化或迁移，也没有新增事务清理路径。

工程检查：问答模块 140 项、全部 API 373 项、前端 11 项、评测环境工具 5 项测试通过；前后端构建通过，前端保留已有大包提示。修改文件格式、文档链接、配置和差异检查通过。实验语料、脚本与失败记录位于本机忽略目录 `reports/answer-repair/2026-11-23-r1/`，不进入业务提交。密钥没有复制，主项目未重启，代码尚未提交或合并。
