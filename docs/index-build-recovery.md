# 索引构建进度与失败恢复

本阶段降低构建失败后的重复模型计算，并保存可查询的构建阶段。索引可见性仍由 [generation 协议](pipeline.md#索引版本与可见批次) 控制；本表不是任务队列或激活依据。

## 向量按成功批次保存

此前向量请求已经按条数、字符数与并发分批，但要等整份文档成功后才保存缓存。最后一批失败时，之前成功批次的向量也没有保存。

现在每批返回后先校验条数、维度、有限数值及非零模长，再立即保存到 MongoDB。后续批次失败时停止发起新请求，并等待已经在途的请求和保存操作结束。已成功保存的批次可供新服务实例或消息重试复用；进程在保存前被终止时，该批次仍会重算。

复用范围与模型修订要求见 [ingestion.md](ingestion.md#向量与写入预算)。`EMBEDDING_MODEL_REVISION` 为空时继续禁用持久向量缓存。缓存故障只影响复用，成功构建仍可继续；短暂保存失败会在本次向量调用完整成功后补存。进度计数包含原始 Chunk 的重复输入数量，实际模型请求会去重。进度表示已获得有效向量的数量，缓存保存失败时不能把进度当作可恢复数量。

重试会创建新的 generation，重新写入完整 ES 索引并完成 refresh 后才尝试激活。此能力不提供 ES bulk 续写，也不提供 KG 模型抽取断点。成功保存的单批向量不是可检索的半成品索引。

## 构建状态

PostgreSQL `kh_index_build_progress` 按 generation 保存一次尝试，记录文档修订、正文 ID、管线、阶段、计数及时间。正文读取、分块、向量生成或图谱抽取的失败也在本次尝试内记录，避免仅记录索引写入阶段。

| 状态                 | 含义                                                                        |
| -------------------- | --------------------------------------------------------------------------- |
| `running`            | 尝试已开始；阶段与更新时间是最近成功保存的观察                              |
| `succeeded`          | 本次 generation 已通过激活检查                                              |
| `failed`             | 准备或暂存阶段失败，已尝试清理本次 generation                               |
| `superseded`         | 最终版本或删除检查拒绝激活，已尝试清理本次 generation                       |
| `activation_unknown` | 激活调用报错，提交结果不确定；保留暂存数据，避免误删可能已激活的 generation |

阶段按 `preparing → content → chunk → embedding / graph_extract → index_write → activating → complete` 推进。计数是当前阶段的单位数，换阶段可重置；全文写入的单位是文档，RAG/KG 是 Chunk。相同阶段的完成数不会被迟到回调降低，终态不允许改写。ES/KG 写入目前只有开始与完成计数，没有逐请求计数。无模型修订的向量路径仅报告整次调用完成数。

状态写入失败会记录不含正文和提供方错误的警告，不改变 generation 激活结果。进程被强制终止可能保留 `running`；当前没有独立心跳和自动超时判定，必须结合 `updated_at` 与消息消费状态排查，不能仅凭它判断任务仍在执行。消息重试和死信沿用已有 Outbox/receipt。

每次结束构建，最多清理 200 条超过 30 天且已有更新尝试的旧状态；每份文档每条管线的最新状态始终保留，包括未确认的崩溃状态。删除文档会级联删除其状态，迟到的 UPDATE 或旧快照不会重新创建记录。状态清理不删除索引或 generation 指针。

## 查询与授权

```http
GET /api/v1/documents/<document-uuid>/index-status
Authorization: Bearer <token>
```

仅文档上传者或管理员在具有查看权限时可以访问，缺失文档返回 404。返回文档当前 `version` 和各管线最新一次尝试 `attempts`，其中 `currentVersion` 表明尝试是否属于当前修订。不返回正文、向量、凭证或外部服务原始错误。尚未开始构建时列表为空；迁移不会回填历史尝试。

最新一次失败不表示旧完整索引不可用；历史成功也不表示该修订仍然发布。实际可查询性仍需检查当前发布状态与 `kh_index_head`。文档详情页已提供按需查询与刷新入口，显示最近尝试及其版本；批量管理另见 [受控索引升级](index-upgrades.md)。

## 升级与回滚

新数据库初始化会执行 009。已有数据库在应用既有迁移后执行：

```bash
psql "$KNOWBASE_DATABASE_URL" -v ON_ERROR_STOP=1 -f deploy/postgres/migrations/009_index_build_progress.sql
```

先执行迁移，再部署新 API/Worker。脚本可重复执行。无需改写现有向量缓存和索引，也不会自动对存量文档发起重建。回滚代码时可以保留新增状态表；旧代码不读取它。删除该表会丢失观察记录，不影响已激活的 generation。

## 可重复验收

```bash
pnpm --filter @knowbase/api test:ingestion
pnpm --filter @knowbase/api test:index-consistency
```

前者使用真实隔离 MongoDB，比对两种保存策略，并启动独立 Node 进程，在确认 4 条向量已保存后发送 SIGKILL，随后用新服务实例验证只计算剩余 2 条。后者使用真实 PostgreSQL、Elasticsearch 与 Neo4j，验证进度并发不回退、终态不可改写、旧版本拒绝、删除级联、历史清理和原有可见性约束。

对比使用相同的 6 条合成业务文本、每批 2 条、并发 1，在第三批注入失败。旧策略通过不传递逐批回调复现“整次调用成功后保存”的行为，其他代码与数据一致。模型为确定性替身，数据库是真实 MongoDB；测量实际交给替身的文本数，不测量真实模型延迟或语义质量。

| 指标                                 | 整次成功后保存 | 每批成功后保存 |
| ------------------------------------ | -------------: | -------------: |
| 失败后已保存向量                     |              0 |              4 |
| 首次失败尝试请求的文本数（含失败批） |              6 |              6 |
| 重试请求的文本数                     |              6 |              2 |
| 随后完整重复构建请求的文本数         |              0 |              0 |
| 修改一条文本后请求的文本数           |              1 |              1 |
| 最终向量内容与顺序                   |           正确 |           正确 |

该故障位置下，重试模型输入减少 66.7%；包含首次失败尝试时，总输入从 12 条降至 8 条，减少 33.3%。这不是生产耗时提升比例，收益取决于失败位置、批次、缓存可用性及模型修订配置。生成报告位于忽略目录 `reports/ingestion-index-recovery/comparison.json`。

存量文档的预览、限速、版本冲突跳过、进度汇总及失败重试已进入 [阶段 4 受控索引升级](index-upgrades.md)，隔离验收见 [演练报告](index-upgrades-report.md)。阶段 3 的上述对比保留为历史基线。
