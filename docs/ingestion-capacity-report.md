# 固定负载容量基线（6.2.2）

本轮以固定合成输入测量 HTTP 上传 → 异步解析 → 审核发布 → search/rag/kg 当前版本全部激活，随后核验正文、原件摘要、事实 Chunk 和删除清理。目的是为后续性能改动提供可比较基线，不是生产容量承诺。

## 运行方法与边界

```sh
npm run build --workspace apps/api
node --test apps/api/test/ingestion/capacity/metrics.test.cjs
CAPACITY_OUTPUT=reports/ingestion-capacity/your-new-run \
DELIVERY_TEST_PULL_POLICY=never \
node apps/api/test/ingestion/capacity/run.cjs
```

输出目录不能已存在，避免覆盖证据。首次运行需先准备 Compose 指定的镜像，或者省略 `DELIVERY_TEST_PULL_POLICY=never`。脚本创建独立 Compose 项目及随机端口，结束时删除自己的容器和卷，不复用其他会话环境。源码、编译产物、工具、部署文件、镜像 ID 和输入 SHA-256 均记录在机器报告。报告保留运行时 dirty 状态，不冒充已经提交的运行。

- 文件：16 KiB、64 KiB ASCII TXT，各并发档 20 份，每份有唯一序号；2 份预热不计入结果。TXT 没有页数，不推算 PDF 页数。
- 客户端并发：1 / 4 / 8；封闭循环，每个槽位包含上传、解析轮询、审核发布、索引轮询和回读。吞吐分母包含回读；单文档端到端延迟截止全部激活，另存回读耗时。删除不计入吞吐时间。
- 后台：单应用进程，每个 RabbitMQ consumer prefetch=1，Outbox 轮询 1000 ms、每轮最多 20 条，分块 1000/150。每档使用新文档 ID，无跨文档缓存复用。
- 服务：真实 PostgreSQL、MongoDB、RabbitMQ、RustFS、ES、Neo4j。各容器最多 1 CPU；内存上限依次为 512、768、512、768、1024、768 MiB。应用在宿主运行，V8 heap 上限 512 MiB，没有独占 CPU 或 RSS 限制。
- 模型：原生 TXT 解析、确定性 768 维非零向量、空实体/关系抽取，仅隔离基础设施负载。图谱仍写入真实文档/Chunk。不代表 MinerU OCR、Embedding 或 KG 真实模型速度与质量。模型质量依据此前独立报告。
- 采样：每轮等待 500 ms 后开始下一轮，非重叠采样；报告实际采样间隔和耗时。记录 Node RSS/heap/CPU/事件循环、应用实际连接池上限/等待数、PG 活动/事务/锁、Outbox 和 RabbitMQ ready/unacked。RabbitMQ 管理统计刷新 500 ms；短峰值可能漏采，字段缺测保持未知，请求错误单独计数。PG 连接数只排除当次采样查询，仍包含其他测试观测连接；应用池单独统计。RSS 仅为 Node 进程，不含容器总内存。
- 分位数：逐档 nearest-rank 经验 P50/P95，每档只有 20 份，尚不足以推断稳定尾延迟。阶段日志按文档 ID 筛选，并保留阶段自己的样本数；一次文档可能因两条管线首次同时 miss 而生成两次 chunk 记录，不能误当独立文档。

原生 parse 日志仅覆盖解析器，chunk 日志不含缓存读写，embedding 日志包含替身调用但不完整覆盖缓存；index.write 当前只记录 RAG，index.activate 覆盖三条管线。端到端时间包含这些日志之外的等待、保存和协调，不能把阶段分位数相加，也不能仅凭一条阶段日志断定总耗时归因。

## 验收记录

首轮预热曾因测试过早检查异步删除而失败。脚本已改为等待五类 Mongo 记录、两类 ES 索引、图谱、原件及 tombstone 均核对完成。失败日志位于本机 `reports/ingestion-capacity/fixed-load-first`，不会作为容量通过数据。

2026-11-27 最终运行：**6 档 × 20 份 = 120/120 通过**，另有 2 份预热。原件摘要与正文逐份回读一致，关键事实进入带来源范围的 Chunk，三条当前版本 generation 激活，所有删除检查通过；独立容器与卷已移除。逐文档输入摘要、阶段分布、采样数量和资源记录见 [机器基线](baselines/ingestion-capacity-2026-11-27.json)。完整本机证据位于 `reports/ingestion-capacity/fixed-load-final`。

宿主为 Darwin arm64、10 逻辑 CPU、24 GiB 内存、Node v24.16.0；Docker VM 为 10 CPU、约 7.75 GiB 内存。其他会话同时使用这台开发机，未暂停它们。这些数据用于本环境后续比较，需要在独占部署资源和实际语料上另行确认。

每份 16 KiB 文件生成 18 个 Chunk，64 KiB 文件生成 71 个 Chunk。采样错误、RETRY/DEAD receipt 采样峰值、连接池等待和 PG 锁等待均为 0；应用池上限 10，实际连接峰值各档为 7/8/10 和 7/9/10。采样中仍可见最多 4 个 idle-in-transaction，不能表述为没有跨外部调用持有事务，也不能由此证明高并发一定不堵塞。

## 判断与后续顺序

1. **当前配置下并发 4 已接近本轮吞吐平台。** 并发 4→8，16 KiB 吞吐 0.936→0.925，64 KiB 0.933→0.926；P95 则从 4.20→8.95 秒、4.28→8.48 秒。后续比较先固定并发 4，生产并发阈值需另测，不能直接扩大客户端并发宣称提速。
2. **暂不扩大连接池或重构 receipt 租约。** 采样没有持续池等待/锁等待证据；存在空闲事务值得关注，但本轮不足以将其认定为主瓶颈。真正出现连接等待时再做租约方案对照。
3. **补测索引写入与刷新等待，优先于重写解析器。** 原生 parse 与 chunk 均远低于端到端秒级等待；search 写入使用 `refresh: wait_for`，且每 consumer prefetch=1，是后续单变量对照的候选。当前没有单独覆盖 search 写入的阶段日志，尚不能把平台根因定为 ES 刷新，需补齐该测量后比较，保留发布后可检索的约束。
4. **重复分块登记为次级优化项。** 120 份文档产生 157 次 chunk 完成记录，额外 37 次来自首次 RAG/KG 缓存 miss 交错。本轮无失败重试。可以评测文档/内容/策略相同 key 的进程内进行中请求复用，先记录省下的缓存写入与内存成本；当前解析/分块计算很短，不能用 37 次减少量推导端到端提速。
5. **下一交付仍是 6.3 发布与回滚演练。** 这份基线先冻结；上线容量验收还需真实 MinerU/Ollama、复杂 PDF/大表格、超过 8 并发的开放到达率及长时间运行。本轮不声称这些场景通过，也没有修改另一分支的召回、重排或 Prompt。
