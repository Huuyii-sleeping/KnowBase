# 构建流程真实服务评测

2026-11-22，在 Apple M4 / macOS arm64、Node 24.16.0 上串行执行。使用真实 Ollama `nomic-embed-text:latest`（768 维）、MongoDB 8.2.12、Elasticsearch 8.15.3；数据库位于本次专属临时 Docker 项目，结束后全部移除。基线为实际 Git `955f1e17a0717cc13eb538f7062544444c70f220` 中的 Embedding 服务和 ES writer，新版为当前未提交工作区。每个场景 3 轮，表内耗时取中位数；样本量不足以报告 P95 或生产吞吐。

结论：向量去重与持久复用已测得收益；分块持久缓存尚未获得速度收益；ES 分批减少请求峰值，但本轮总耗时略增。解析/OCR 与结构质量的比较见 [ingestion-comparison.md](ingestion-comparison.md)。

## 向量去重、缓存与失效

固定 96 条文本，其中 48 条不同文本，共 33,484 字符。模型先预热；每次新版调用都重建应用服务实例，通过真实 MongoDB 读取持久缓存。新旧调用顺序逐轮交替，记录实际 `/api/embed` 请求，而不是模拟提供方计数。模型 digest：`0a109f422b47e3a30ba2b10eca18548e944e8a23073ee3f3e947efcf3c45e59f`。

| 场景                             | 旧版模型输入 | 新版模型输入 | 旧版耗时 ms | 新版耗时 ms | HTTP 请求旧→新 |
| -------------------------------- | -----------: | -----------: | ----------: | ----------: | -------------: |
| 冷应用缓存首次构建               |           96 |           48 |     3827.43 |     1613.06 |            1→2 |
| 同文档未修改重建                 |           96 |            0 |     2792.50 |       14.80 |            1→0 |
| 修改一条不同文本（两个重复位置） |           96 |            1 |     2537.75 |       74.62 |            1→1 |
| 模型配置指纹失效                 |           96 |           48 |     2610.62 |     1344.15 |            1→2 |
| 不同文档的相同文本               |           96 |           48 |     3170.22 |     1387.11 |            1→2 |

首次构建耗时降低 57.9%；未修改重建降低 99.47%；局部修改降低 97.06%。这些是本机合成文本的中位数变化，不能当作生产 SLA。基线个别轮次有 27–33 秒长尾，逐轮数值保留在原始报告；不据此推断长尾原因。Ollama 自身可能缓存重复文本，本评测不关闭或更改共享模型服务；冷缓存指应用 MongoDB 缓存为空，不指模型进程冷启动。

本次所有返回向量与旧版同一输入逐项比较，最大绝对差为 **0**；输出顺序与重复位置均一致。这证明本次去重/复用没有改变向量，不证明检索 Recall/MRR 提升。新版每请求最多 32 条输入，观察到最多并发 2；拆批会增加 HTTP 请求数，模型输入总量才是去重收益指标。

指纹失效场景只改变应用的修订标识，未实际替换模型权重；验证的是旧缓存不会被复用。另一个文档仍需计算，未跨权限范围共享。删除本次文档后缓存记录为 0，另一文档仍保留 48 条，最后一并清理。

**启用条件：** `EMBEDDING_MODEL_REVISION` 必须填部署模型的不可变 digest/修订。示例配置留空时禁用持久向量缓存，但单次去重和批次限制仍生效；本表缓存收益不是空配置下自动获得的。模型权重变更时必须同步更新修订，规则见 [入库配置](ingestion.md#向量与写入预算)。

## 分块产物复用：有计算节省，存在耗时回退

383,168 字符（383 KB）的合成 Markdown，300 个章节，生成 900 个结构 Chunk。为了单独测量复用成本，两侧均使用相同的新版分块算法：对照直接计算两次，新版由两个依次执行的服务实例读取/写入 MongoDB 分块产物。此处不是旧 Git 分块算法的对比。

| 指标                     | 不使用持久产物 |  使用持久产物 |
| ------------------------ | -------------: | ------------: |
| 两个消费者的分块计算次数 |              2 |             1 |
| 两次消费总耗时中位数     |       30.03 ms |     229.72 ms |
| 新版首次消费中位数       |              — |     188.68 ms |
| 新版缓存命中消费中位数   |              — |      49.07 ms |
| Chunk 数量及内容摘要     |  900，完全一致 | 900，完全一致 |

MongoDB 的 900 条分块写入、清单发布、读取、序列化与摘要校验成本超过了这份样本的纯计算成本。因此，当前持久产物的价值是统一 RAG/KG 产物、跨实例复用以及完整性校验，**不能宣称分块提速**。后续应测不同规模与消费并发，再选择按成本启用持久化、或增加有界的进程内共享；本次未用内存命中掩盖数据库成本。两个消费者依次执行，不证明同时首次请求只计算一次。删除后本次分块记录为 0。

## ES 批次边界：请求峰值下降，总耗时未改善

真实 ES dense_vector/HNSW 索引写入 1000 个 Chunk，向量为确定性非零合成 768 维数组，本段不包含模型推理。两侧使用相同当前 schema；预建索引，计时包含 mapping 检查、bulk 及最终刷新，返回后立即校验 1000 条均可搜索。一组预热后再交替运行 3 轮。

| 指标                 |        旧版 |        新版 |
| -------------------- | ----------: | ----------: |
| 单次请求最多 Chunk   |        1000 |         200 |
| bulk 请求次数        |           1 |           5 |
| 最大 NDJSON 请求大小 | 7,852,983 B | 1,570,667 B |
| 总耗时中位数         |  1029.26 ms |  1240.84 ms |
| 立即可搜索数量       |   1000/1000 |   1000/1000 |

单次序列化请求峰值降低约 80.0%，中位总耗时增加约 20.6%；轮次范围分别为 1029–2181 ms 和 786–1557 ms，不能据 3 轮断言吞吐变化。新版所有 bulk 使用 `refresh:false`，最后显式 refresh 一次；旧版单 bulk 使用 `wait_for`。请求峰值是压缩前 NDJSON 字节数，不是峰值进程内存；总传输量没有实质减少（索引名字长度差异造成总字节相差 1000）。

本实现仍持有完整 chunks/vectors 数组，分批只限制单次 ES 请求和构造中的 operations；尚未实现端到端流式入库。收益主要是有界请求与失败后禁止半成品激活。真实后续批次失败、refresh/激活和版本一致性由索引集成测试独立覆盖。

## 异步任务与清理：验证可靠性，不虚构速度指标

最新回归包括 PostgreSQL/RabbitMQ 解析任务 6 项、投递可靠性 8 项、PG/ES/Neo4j 索引一致性 14 项、MongoDB 持久化 5 项，以及真实六格式合成回归 2 项。解析任务和清理测试中的解析器/资源存储使用小型 fake；数据库、队列及指定索引服务为真实容器。它们验证以下约束，不构成生产吞吐测试：

- 原文件提交后的元数据、任务及 Outbox 原子保存；重复投递只有一个任务持有者。
- 租约过期恢复已有远端任务，旧 token 不能采用结果；超过重试预算停止。
- 手动编辑、取消、重解析和删除不会被旧结果覆盖。
- 失败资源清理可重试；清理完成前保留资源引用，已采用的历史正文不被尝试回收误删。
- 分批写入中途失败仍保留旧 generation 的可见性；退休回收保留当前及暂存数据，清理失败保留重试记录。

尚未测量生产上传响应分布、Worker 并发吞吐、真实对象存储补偿耗时、长文档端到端峰值内存，或固定召回/重排版本下的检索质量。这些是下一轮验收项。

## 复现

已安装并运行本地 Ollama，预先缓存 `mongo:8` 和 `elasticsearch:8.15.3` 镜像后：

```bash
pnpm --filter @knowbase/api benchmark:ingestion-performance
```

脚本自动读取本机模型 digest，采用独立容器项目，结束后销毁数据库，不连接应用数据库。支持 `OLLAMA_BASE_URL`、`OLLAMA_EMBEDDING_MODEL` 和第一个位置参数基线 Git ref。当前夹具预期模型维度 768，不会自动下载模型或改动共享模型配置。

[原始报告](../reports/ingestion-performance/comparison.json) 包含版本、环境、逐轮时间、实际 HTTP 模型输入计数、请求峰值及一致性校验。报告目录被 Git 忽略，不含正文或向量。基准脚本按环境、分块、Embedding、ES 拆分职责；内置断言确保未命中数、顺序、维度、批次边界与可见数量满足预期。
